# yorozu-fx — DaVinci Resolveプラグイン仕様

仕様版: 1.0 / 策定日: 2026-11-07 / 製品名・リポジトリ名: yorozu-fx

本書は[原構想書](Color_Mixing_Studio_Functional_Spec_v1.0.docx.md)のレビュー、競合調査、差別化案の評価、その結果として採用する製品仕様をまとめたものである。対象は開発・画作り・品質評価・製品企画担当者。原構想書は保存し、今後のプラグイン開発には本書を優先する。

「採用」は仕様上の決定を意味し、実装済み・需要検証済み・ホスト検証済みを意味しない。競合情報は公開一次資料を2026-11-07に確認した範囲であり、製品の実機比較、全機能の網羅、特許調査は行っていない。以下の点数・費用・期間・販売価格は企画上の仮説である。

## 1. 製品判断

**Resolve内で、複数の独自ルックを混ぜながら、肌・ニュートラル・指定した色を必要なだけ残し、同じレシピを他ショットや別環境へ再現するOFXプラグインを作る。**

訴求は「12色」「多項式」「フィルムらしさ」ではなく、**混ぜる・残す・再現する**の一連の操作に置く。初版は6基底から最大3つを選ぶミキサー、色とトーンの独立強度、色域による保護、再現可能な候補生成、版付きレシピ、検証付きLUT出力に絞る。

初版の作業空間はDaVinci Wide Gamut / DaVinci Intermediate（以下DWG/DI）、仕上がりの正式評価対象はRec.709 Gamma 2.4のSDR。入力と出力は同じDWG/DIであり、カメラ変換や出力レンダリングはResolveが担う。広色域の作業空間を扱うことと、HDR納品対応は区別する。

### 1.1 前提と成功条件

| 前提・問い | 判断 | 理由・確認方法 |
| --- | --- | --- |
| 主製品はWeb写真アプリか、Resolveプラグインか | Resolveプラグイン | 今回の依頼を優先。素材管理・コーデック・スコープ・書き出しの再実装を避ける |
| 12基底が必要か | 初版は6、同時使用3 | 数では差別化できない。区別できる画作りと混合品質を先に成立させる |
| 多項式である必要があるか | 必須にしない | ユーザー価値は画質と操作。初版は共通格子の基底LUT合成とする |
| DCTLが前提か | OFXを採用 | パラメータ永続化、レシピ入出力、候補操作を一製品にまとめる |
| 自動でショットが一致する必要があるか | 初版は不要 | 技術的なカメラ合わせと露出合わせは事前作業。共通レシピは一致の保証ではない |
| 顧客は誰か | 中級の個人映像制作者・小規模ポスト | 手動グレーディングは理解しているが、作品ルックの探索と修正を短縮したい層 |

本質的な課題は「映像を編集できない」ではなく、「複数の見た目を試すと、残したい色まで変わり、別ショットへの展開や後日の再現に手間がかかる」ことである。成功は機能数ではなく、この作業の時間・修正回数・再現誤差で判定する。

### 3.2 狙う市場の隙間

狙うのは「高忠実度のフィルム再現」ではなく、**制作者自身のルックを探索し、保護条件を維持したまま修正し、再現可能な形で渡す作業**である。色域保護、レシピ固定、出力検証の組合せが、混色を実務で使う際の修正負担を減らすと仮説を置く。

容易に模倣されるUIだけに依存せず、独自基底の画質、混合時の破綻を含む試験素材、旧版再現、明確な色空間契約を積み上げる。これも参入障壁になるという仮説であり、「世界初」「競合にない」「肌が絶対に変わらない」とは訴求しない。

### 4.1 各案の詳細評価

#### I01 — 3ルックの役割付きミキサー

- **価値と操作:** 6基底からBase・Accent・Finishの3枠へ選び、比率と全体量を調整する。12本の同時スライダーより探索の出発点が分かりやすい。
- **差と限界:** 混色自体はMonetと重なる。役割名は操作ガイドであり独自の処理方式ではない。枠順を処理順にして複雑化しない。
- **実現性と負担:** 標準choiceとdoubleパラメータで実現できる。初版に三角形UIを要求しないためホスト依存が小さい。
- **検証と決定:** 初見ユーザーの80%以上が説明10分後に2ルック混合を完成できること。初版採用。基底の個性が弱ければUI追加より画作りをやり直す。

#### I02 — 色とトーンの独立強度

- **価値と操作:** 色合いは気に入るがコントラストが強すぎる、という修正を2つの量で扱う。
- **差と限界:** MONONODES等にも近い操作があり、単独では差別化にならない。知覚明度と測光輝度は同じではなく、「色操作で明るさが絶対不変」とは保証しない。
- **実現性と負担:** 合成ルックと入力を同一OKLab座標へ変換してLとa,bの差分を別倍率にする。DWGをsRGB行列へ直接入れない。
- **検証と決定:** 色量0でa,b差分ゼロ、トーン量0でL差分ゼロを参照計算で確認。初版採用。物理フィルムモデルは要求しない。

#### I03 — 保護アンカー

- **価値と操作:** 肌色域、ニュートラル、任意の1色域を指定し、ルックが加えた色差を弱める。商品色や衣装を残したい案件を狙う。
- **差と限界:** Qualifierや色相範囲調整の代替は存在する。違いは保護条件を設定したまま混色・候補探索・保存・LUT化できる一連の操作。似た色の背景も保護されるため、物体認識の代用にはならない。
- **実現性と負担:** 入力画素だけに基づく連続マスクを使う。初版の指定色は色相・相対クロマの数値指定であり、画面上のスポイト取得は必須にしない。
- **検証と決定:** 色域中心における差分抑制量、境界の連続性、多様な肌と照明、木材・夕景への誤保護を評価する。主差別化として採用。画素マスクの限界は製品説明へ明記する。

#### I04 — 保護条件を固定した候補探索

- **価値と操作:** レシピの周辺を3候補だけ試す。保護量・色/トーン量・全体量を変えず、混合比率だけを動かす。
- **差と限界:** ランダムプリセット自体は弱い。確定値保存、変更対象の限定、元へ戻せる操作をまとめる。画像を理解して「良い候補」を選ぶAIではない。
- **実現性と負担:** 固定PRNGと固定候補生成式で実現。3候補は順番に適用・比較し、同時サムネイルは作らない。
- **検証と決定:** 同seedで同じ候補、ロック値不変、1回のUndoで復元。採用。「保護」は指定色域の差分抑制であり候補の美的品質保証ではない。

#### I05 — 露出耐性表示

- **価値と操作:** 現在レシピへ±2 EVの標準テストを行い、肌色相や白の変化を示してショット展開前の手掛かりにする。
- **差と限界:** 評価対象を固定すれば説明可能な品質情報になるが、照明やカメラの異なる実映像の安定性までは分からない。
- **実現性と負担:** チャートによる処理は可能だが、恣意的な総合「安全スコア」を作る危険がある。先に測定量と表示の理解を検証する。
- **検証と決定:** 露出別の色差・階調を個別表示し、実素材の問題検出と相関するか調査。v1は開発用試験に使い、顧客向け機能はv1.1候補とする。

#### I06 — ショット群の一貫性診断

- **価値と操作:** 複数の代表フレームから修正の必要なショットを見つける。反復案件では価値が高い。
- **差と限界:** AIグレーディングやResolveの共有ノード等と重なる。画が異なるショットを同じ分布へ寄せると作品意図を壊す。
- **実現性と負担:** 通常の単一OFXはタイムライン全体へ自由にアクセスできる前提を置けない。別の素材投入UIや補助アプリが必要になり、範囲が膨らむ。
- **検証と決定:** ホストAPI、許諾済み代表フレーム、意図した例外指定を確認してからv2で判断。初版は共通レシピの手動展開のみ。

#### I07 — 版固定レシピ

- **価値と操作:** 数か月後や別マシンで、同じルックと保護条件を再現する。レシピ間の設定差も読める。
- **差と限界:** 保存そのものは標準機能。エンジン・基底・補間方式まで特定し、欠落時に無言置換しない点を品質上の差とする。OSやODTの違いによる表示差は別問題。
- **実現性と負担:** ホストの永続パラメータと移植用JSONを併用。旧エンジンを保守する継続費用がある。
- **検証と決定:** 別環境での再読込、旧版読込、欠落・破損時の失敗動作を検証して採用。出荷後の画作り修正を同じ版へ上書きしない。

#### I08 — 検証付きLUT

- **価値と操作:** OFXのない環境へ、指定空間における静的なポイント変換を渡せる。誤差と適用条件を添付する。
- **差と限界:** LUT出力は競合にもある。比較セット、補間方式、合否をレシピと結び付ける運用品質を狙う。cube自体は色空間を強制できず、移送後の誤配置も防げない。
- **実現性と負担:** 同じ評価関数で格子全体をサンプリングする。LUT生成だけを別の近似実装にしない。
- **検証と決定:** 格子外の検証点とResolve実機で基準を満たしたものだけ「検証済み」とする。初版採用。HDRやカメラ変換入りLUTは対象外。

#### I09 — 入力空間の自動診断

- **価値と操作:** 間違った空間への適用や二重ODTを防ぐ。初学者の失敗を減らせる。
- **差と限界:** 入力プロファイル対応は競合にもある。画素の見た目だけではLog種類や既適用変換を確定できない。
- **実現性と負担:** OFXがプロジェクト設定や前後ノードを常に取得できるとは限らない。自動「正常」表示は誤認を招く。
- **検証と決定:** v1はDWG/DI固定ラベルと配置ガイド、ユーザー確認に限定。表示は「ユーザー確認済み」であり「自動検証済み」ではない。APIで根拠を取れる場合だけ自動診断を追加する。

#### I10 — 参照画像からの配合提案

- **価値と操作:** 作品の参考画像から初期配合を得る。入口としては魅力がある。
- **差と限界:** Colourlab等の競争が強い。照明・被写体・構図による差をルック差と誤認しやすく、6基底の凸結合では任意の参考画像を再現できない。
- **実現性と負担:** 最適化、素材権利、結果説明、処理時間の設計が必要。自前の基底品質評価より先に行わない。
- **検証と決定:** 初版不採用。将来は自作・許諾済み参考画像に限定し、「近い出発点」の提案として別途評価する。

#### I11 — HDR版

- **価値と操作:** SDRで作った意図をHDRでも仕上げやすくする。納品用途の拡大が期待できる。
- **差と限界:** DWG/DIへ入出力できるだけではHDRの画質は保証されない。ピーク輝度、サラウンド、色域、知覚モデルの評価が要る。
- **実現性と負担:** HDRモニターと独立の基準画像、PQ/HLG検証が必要。SDR用OKLab閾値をそのまま使う判断はしない。
- **検証と決定:** 初版保留。既存レシピの出力を黙って変更せず、別エンジンIDまたは明示モードで追加する。

#### I12 — フィルム質感・実在銘柄

- **価値と操作:** 粒子や発光で手軽にフィルム調へ仕上げる需要はある。
- **差と限界:** Resolve内蔵、Dehancer、Nitrate等が充実。yorozu-fxの購入理由が埋もれ、実測のない銘柄再現は品質主張も弱い。
- **実現性と負担:** 空間処理・時系列・解像度依存が入り、LUTとの一致が崩れる。混色エンジンの検証も複雑になる。
- **検証と決定:** 不採用。既存の粒子・ハレーションをyorozu-fxの後段等で使う配置例を提供する。物理顔料・実在フィルムの再現とは称さない。

## 6. ユーザーの作業と配置契約

1. Resolve側で入力カメラ空間を指定し、露出とWBを整える。
2. DWG/DIのノード領域へyorozu-fxを配置する。
3. Baseを選び、必要ならAccentとFinishを足す。ToneとColorを調整する。
4. 肌・ニュートラル・指定色の保護を調整する。必要なら固定3候補を比較する。
5. Gallery等で他ショットを確認し、ショット側の補正で整える。
6. プロジェクト保存、必要に応じレシピまたは検証付きLUTを出力する。

```text
RCM（作業空間を手動でDWG/DIに設定）:
入力変換 → Clip露出/WB → yorozu-fx（Clip または Group Post-Clip）→ 出力変換

非カラーマネージド DaVinci YRGB:
カメラLog → CST［カメラ→DWG/DI］→ 露出/WB → yorozu-fx
          → CST［DWG/DI→Rec.709 Gamma 2.4］
```

**FR-COL-01:** yorozu-fxは入力・出力空間を自動推定しない。固定ラベル `DWG / DaVinci Intermediate → 同一空間` と配置ガイドを常時参照可能にする。確認ボックスは案内用であり、レンダー結果を変えない。

**FR-COL-02:** カメラ変換・トーンマッピング・出力色域圧縮・legal range変換はyorozu-fxへ含めない。RCM設定とCSTによる二重変換を避ける手順を添付する。RCMと手動CSTは、同じ変換設定を用いた試験で照合する。

**FR-COL-03:** タイムライン空間と実際のノード入力空間が一致することをユーザーが確認する。Rec.709やsRGBへDWG/DI用ルックを直接適用する使用法は非対応。ACES利用者には、初版の正式対応外と明示する。

### 7.2 混合とゼロ境界

**FR-MIX-01:** 正の重みだけを合計し正規化する。Base/Accent/Finishは順次処理ではなく同じ入力への並列ルック。lookIdごとに重みを集約してID順で合算し、同じlookIdを複数枠で選んでも結果が変わらない。

**FR-MIX-02:** 全weight=0、またはStrength=0では厳密なバイパス経路を使う。全ゼロから最初の正weightへの境界は正規化の仕様上不連続である。初期値100/0/0を維持し、徐々に効果を出すにはStrengthを使うよう案内する。見た目だけの時間補間はレンダーへ入れない。

**FR-MIX-03:** 比率、強度、保護は静的。新たな時刻で自動再抽選しない。ホストの任意順レンダー、再シーク、並列レンダーでも同じ画素値を返す。

### 7.3 候補生成

**FR-EXP-01:** 現在の3枠のlookIdを固定し、未ロック枠のweightだけを変更する。新しいlookIdの探索は手動選択で行う。ロック枠は生weightと正規化後の配分の両方を維持するため、未ロック枠のweight合計を保存したまま再配分する。

**FR-EXP-02:** PCG32の参照実装とseed初期化方法を `pcg32-yorozu-fx-v1` として固定する。生成順は候補番号→枠順。未ロック枠の合計W>0について、独立の正の乱数を正規化したベクトルqと現在比率pから `p'=(1-a)p+a*q`（a=Amount/100）を作り、`weight'=W*p'` とする。

**FR-EXP-03:** いずれかのweightが100を超える候補は棄却し、候補あたり最大32回再試行する。生成できなければ元の配分を返して「この範囲では変化を生成できません」と示す。ゼロ合計、未ロック枠が1つ以下、Amount=0では元レシピを返す。

**FR-EXP-04:** 生成時の原本と確定候補3件をホストの非アニメーション永続パラメータへ格納する。候補適用・復元以外の操作でミキサーを編集したら候補を無効化する。候補適用・復元は同じ生成セッション内で行い、候補選択間で原本を上書きしない。レシピへの出力は実際に適用されたweightを正本とし、seedは由来情報とする。

## 9. 色エンジン

### 9.1 基底表現と範囲

**FR-ENG-01:** 初版は共通の65×65×65格子、float32 RGBの残差LUTを使う。格子範囲はDWG/DI符号化値の各軸 `[-0.1, 1.1]`。残差は `基底出力 − 入力` を同じ符号化空間で記録し、四面体補間する。格子・走査順・四面体の分割規則はエンジン版で固定する。

**FR-ENG-02:** これは画作りの初期モデルであり、格子密度自体は画質保証ではない。約20 MBの6基底データを共有し、設定変更時に最大3基底の残差を格子上で合成する。共通格子と同じ補間なら、残差の先行合成と画素ごとの加重和は数学上等価である。浮動小数点差はT05で検証する。

**FR-ENG-03:** 基底範囲外では元の入力値をクリップしない。残差を評価する座標だけを格子範囲内へ収め、次の連続ゲートで残差を弱める。

```text
H(a,b,z) = smoothstep(a,b,z)
g(x) = product over RGB channels j of:
       H(-0.2,-0.1,x[j]) * (1-H(1.1,1.2,x[j]))
delta(x) = tetrahedralLookup(compiledResidual, clamp(x,-0.1,1.1))
proposal = x + g(x) * delta(x)
```

各軸が[-0.1,1.1]内ならg=1。いずれかが-0.2以下または1.2以上ならg=0で元画素を保持する。範囲外で同じルックが続く保証はせず、外挿暴走を避けるため恒等へ戻す。クリップを避けることと、全域で自然な画になることを混同しない。境界の連続性と見え方をT06で検証する。

### 9.2 色・トーン分離と保護の処理順

1. float32 DWG/DI入力を取得し、アルファを分離する。
2. 通常表示でStrength=0、全weight=0、Color/Toneとも0、g=0のいずれかなら入力をそのまま返す。診断表示はこの無効果バイパスより優先して入力からマスクを計算する。
3. 正規化weightで合成した残差からproposalを得る。
4. 入力とproposalを公式DI逆変換→linear DWG→XYZ D65→OKLabへ変換する。
5. 入力LabをA、proposal LabをBとし、`dL=B.L-A.L`、`dab=B.ab-A.ab` を得る。
6. 入力Aだけから§9.3の保護量 `pColor`、`pTone` を作る。
7. `out.L=A.L+s*t*(1-pTone)*dL`、`out.ab=A.ab+s*c*(1-pColor)*dab` とする。
8. OKLab逆変換→XYZ D65→linear DWG→公式DI変換で出力する。元のアルファを戻す。

**FR-ENG-04:** DIの公式関数には低値用の線形分岐がある。負値にlogを直接かけず、公式分岐に従う。DWGの行列・伝達定数はBlackmagicの定義を版固定して使う。[公式DWG/DI仕様](https://documents.blackmagicdesign.com/InformationNotes/DaVinci_Resolve_17_Wide_Gamut_Intermediate.pdf)

**FR-ENG-05:** OKLabの白基準はXYZ D65のY=1、立方根は符号保持とする。sRGB専用行列をDWGへ直接使わない。OKLabはこのSDR評価製品における操作用座標であり、HDR全域の知覚均等性を主張しない。[OKLab原典](https://bottosson.github.io/posts/oklab/)

**FR-ENG-06:** 全無効果時は色空間往復自体を省いて入力を保持する。色域圧縮や出力トーンマッピングは追加しない。負値や1超の出力も浮動小数点でホストへ返す。非有限値の入力・中間値・出力を検知したレンダーはエラーとし、無言の黒置換や不完全な成功を返さない。

### 9.3 保護マスク

入力Labの `C=sqrt(a²+b²)`、`h=atan2(b,a)`、相対クロマ `q=C/max(abs(L),0.05)` を使う。距離dは円周上の色相差の絶対値0–180°。以下の数値はyorozu-fx独自の初期定義であり、肌全般に普遍的な閾値ではない。

- **Neutral:** `N=1-smoothstep(0.02,0.08,q)`。Lや被写体を判別せず、a,b差分だけを抑える。
- **Hue window:** 半幅wについて `U=1-smoothstep(0.8w,w,d)`。
- **Skin:** `K=U_skin * smoothstep(0.02,0.05,q) * (1-smoothstep(0.45,0.60,q))`。
- **Custom:** 中心q0、半径rについて `J=U_custom * (1-smoothstep(0.8r,r,abs(q-q0))) * smoothstep(0.01,0.03,q)`。
- **合成:** `pColor=max(NeutralAmount*N, SkinAmount*K, CustomAmount*J)`。`pTone=CustomAmount*J` はPreserve Tone ON時だけ、それ以外0。

各Amountは0–1。C<1e-6では色相を未定義としSkinとCustomを0、Neutralだけを評価する。保護量を足し合わせて過剰抑制しない。マスクは混合結果で再計算せず、候補や操作順による循環を避ける。

**FR-PROT-01:** 保護100%の意味は「マスク1の画素で、指定成分のルック差分を0にする」である。Neutral100%でも入力に既存の色かぶりがあればそれを除去しない。Skin100%でもトーンは変わる。Customで色とトーンを両方100%保護したマスク中心は、入力を保持する。

**FR-PROT-02:** キー範囲内の物体はすべて作用対象。低彩度・暗部では肌色が区別しにくい。顔や物体を限定したい場合はResolve側で別ノード・キーを使う。マスク表示と保護OFF比較を操作ガイドへ含める。

## 10. ホスト実装・状態・配布

### 10.1 OFXを選ぶ理由

| 形式 | 利点 | 制約 | 判断 |
| --- | --- | --- | --- |
| DCTL + PowerGrade | ポイント処理の試作・配布が軽い | ファイル入出力や候補管理を含む一体的な操作に制約。自由な独自UIは前提にできない | 色の技術試作には可。初版の商品形式にはしない |
| OFX | ホストのパラメータ保存、ボタン操作、CPU/GPU処理、将来拡張をまとめられる | ネイティブ実装・署名・複数GPU・互換性試験の負担 | 採用 |
| Web + 補助サービス | 独自UIを作りやすい | 別アプリ・通信・色表示の照合・二重保存が必要 | 不採用 |

**FR-HOST-01:** C++の共通評価コア、float64のCPU参照、float32の製品CPU経路、Metal/CUDA経路を設ける。GPU処理を宣言するだけで対応とせず、ホストから渡されるバッファ・ストライド・render window・render scaleを実機で検証する。[OpenFX Rendering](https://openfx.readthedocs.io/en/latest/Reference/ofxRendering.html)

**FR-HOST-02:** 合成LUTキャッシュはパックhash・weight・engineVersionで識別し、不変スナップショットとしてレンダーへ渡す。同時インスタンス間で可変設定を共有しない。render action内でファイル読込・設定変更・ネットワーク通信・候補生成を行わない。

**FR-HOST-03:** ホストのalpha/premultiplication宣言に従いstraight RGBで色処理する。premultiplied入力はalpha>1e-6で除算し、処理後に乗算する。alpha≤1e-6のpremultiplied画素は元のRGBAを保持する。straight入力の透明画素はRGBを処理し、alphaは保持する。ホスト契約と異なる二重premultiplyを禁止する。

**FR-HOST-04:** レンダー中のGPU失敗はホストへエラーを返す。異なる画素やタイルを無断でCPU結果に差し替えない。CPUを選ぶ場合は再レンダー開始時に経路を固定し、低速になることを表示する。CPU代替時の実時間再生は保証しない。

### 10.2 永続化と互換性

**FR-SAVE-01:** 現在の画に必要な値はすべてホストが保存するOFXパラメータへ含める。メモリキャッシュやユーザー設定ファイルだけに保持しない。基底データ本体は製品資産に置き、パックID・版・hashをパラメータに保存する。[OpenFX Effect Parameters](https://openfx.readthedocs.io/en/main/Reference/ofxParameter.html)

**FR-SAVE-02:** `pluginIdentifier`、パラメータ内部ID、choiceの数値とlookIdの対応を出荷後に再利用・並べ替えしない。新項目は互換性を維持して追加する。旧評価関数を残し、レシピの構造移行だけで画を変更しない。

**FR-SAVE-03:** 旧パックは同梱保守を基本とする。利用できないengine/pack/hashは明示的エラーとし、現在版へ置換しない。新エンジンへの変更は複製したノードで明示操作とし、旧設定へ戻れるようにする。

### 10.3 配布

macOSは署名・公証、Windowsは署名済みインストーラーを出荷成果物とする。更新はユーザー操作で行い、レンダー中の自動更新はしない。オフラインで編集・保存・レンダー可能にする。初版はローカルライセンスファイル方式とし、レンダー中のオンライン認証を要求しない。販売基盤の選定やライセンス発行処理はこの色エンジンの実装範囲から分ける。

ライセンス欠落・破損は明示的エラーとし、無言の透かし混入や正常出力への偽装をしない。体験版を提供する場合は別途その挙動を定義する。テレメトリ・素材送信・レシピ送信は初版で行わない。

## 11. レシピとLUT

### 11.1 移植用レシピ

拡張子は `.yorozu-fxrecipe.json`。素材・クリップID・ファイルパス・ホストプロジェクト全体は含めない。組込みプリセットも同じ設定スキーマから作る。プリセットには推奨配置と意図を付記する。

```json
{
  "schemaVersion": 1,
  "engineVersion": "yorozu-fx-dwg-sdr-1.0.0",
  "lookPack": {
    "id": "yorozu-fx-original-dwg",
    "version": "1.0.0",
    "sha256": "<release-generated-sha256>"
  },
  "workingSpace": "davinci-wide-gamut/intermediate",
  "mixer": {
    "slots": [
      {"lookId": "L05", "weight": 60, "locked": false},
      {"lookId": "L03", "weight": 30, "locked": false},
      {"lookId": "L07", "weight": 10, "locked": true}
    ],
    "strength": 0.65,
    "colorAmount": 1.0,
    "toneAmount": 0.5
  },
  "protection": {
    "neutral": 0.5,
    "skin": {"amount": 0.5, "hue": 45, "halfWidth": 25},
    "custom": {
      "amount": 0.0, "hue": 30, "halfWidth": 15,
      "relativeChroma": 0.25, "radius": 0.15, "preserveTone": false
    },
    "maskVersion": "yorozu-fx-relative-oklab-1"
  },
  "explorationProvenance": {"seed": 42, "generator": "pcg32-yorozu-fx-v1"}
}
```

上記hashは説明用プレースホルダーであり、有効なレシピではない。製品のエクスポートでは実データの64桁16進SHA-256を入れる。浮動小数点は往復可能な精度で保存する。レシピhashはプロトコル版で固定したキー順・数値表記の正規形から計算する。

**FR-REC-01:** schema、必須キー、3枠、値域、未知enum、hash、ファイル上限1 MiBを検証し、すべて通過してから一括適用する。未知schemaは拒否。任意コード・パス参照・任意shaderを許さない。書込は一時ファイルからの置換で完了し、キャンセル・失敗で既存レシピを壊さない。

**FR-REC-02:** Compareは現在と読込候補のlookId、比率、強度、保護、engine/pack版の差をテキスト表示する。これは数値設定の差であり、画像類似度ではない。ファイル操作は明示ボタンから行い、ダイアログ可否とキャンセル動作をG0で確認する。ホストに依存するダイアログが使えない場合はパス欄＋明示実行ボタンを使う。

### 11.2 LUT出力契約

**FR-LUT-01:** 静的ポイント変換全体をサンプリングし、33または65格子の `.cube` を出力する。入力・出力はDWG/DI符号化値、cube入力領域は各軸0–1。カメラ入力変換・出力変換は含めない。名称に `DWG-DI_to_DWG-DI` と格子数を入れる。

**FR-LUT-02:** cubeはR最速、G、Bの順に格子走査し、小数点以下9桁以上で出力する。出力値が0–1外へ出る場合はそのまま記録し、対象ホストが値を保持するかを検証する。クリップするホストは正式互換先に含めない。0–1外の**入力**については、OFXの§9.1のゲート動作とLUT外挿の一致を保証しない。

**FR-LUT-03:** 出力対象の設定を固定して検証し、検証中の編集が混入しないようにする。33が不合格なら65を案内し、65でも不合格なら検証済みLUTの保存は行わない。検証レポートの保存は可能とする。レシピ保存はLUT不合格でも可能。

**FR-LUT-04:** cubeとレシピと `metadata.json` を1フォルダーへ出力する。metadataはengine/pack/mask版、recipe hash、入力領域、空間、補間方式、試験点seed、誤差、参照出力変換、生成日時を含む。cubeコメントにも最低限の空間契約を記載する。cubeだけで誤配置を防げるとは表示しない。

**FR-LUT-05:** 診断モード、候補一覧、ロック状態、seedは色変換としてLUTへ含めない。lockとseedは同梱レシピの作業情報としてのみ残る。初版には空間・時間・画像全体へ依存する効果を入れないため、通常モードの全色処理が焼込み対象となる。

## 12. 品質・性能・受入試験

すべて今後満たすべき受入値であり、達成済みの測定値ではない。CPU参照はfloat64、製品CPU/GPUはfloat32。符号化値誤差はDWG/DIで測る。視覚誤差は版固定のDWG/DI→Rec.709 Gamma 2.4出力変換後にlinear Rec.709→XYZ D65→OKLabで計算し、`ΔE_OK = 100 * EuclideanDistance` とする。CIEDE2000とは区別する。

参照出力変換のResolve版、CST/RCM設定、トーン/色域マッピング、レンジ、テストプロジェクトをG1で固定する。色差計算は共通出力変換後の有効な表示RGB点で行い、表示域外点を除いた割合も報告する。域外点は有限性・値保持・符号化値誤差で別評価し、除外して合格率を水増ししない。

### 12.1 機能・数値試験

| ID | 対象 | 試験 | 合格基準 |
| --- | --- | --- | --- |
| T01 | 無効果 | 診断OFFでStrength=0、全weight=0、Color/Toneとも0を個別に試す | バイパス時RGBAのビット一致。alpha処理を開始する前に判定 |
| T02 | 比率 | 単独weight=1/100、30:70/15:35、重複ID、枠入替 | DWG/DI最大誤差1e-6以下 |
| T03 | 分離 | Color=0、Tone=0をそれぞれ試す | OKLabで指定成分の差1e-5以下 |
| T04 | 保護 | 各マスクの中心/境界、Amount=0/100、重なり | 中心の保護成分差1e-5以下。重なりはmax式と一致 |
| T05 | 実装一致 | 固定seed10万点、全基底/代表混合、CPU参照対CPU/Metal/CUDA | DWG/DI最大誤差1e-4以下、有効表示点ΔE_OK最大0.1以下 |
| T06 | 連続性 | 範囲[-0.5,1.5]の負値・1超、各ゲート境界、LUTセル境界、0–100%操作を各1000段階 | 非有限値・値の飛びなし。刻み半減で差も収束。ランプの不自然な段差を視覚確認 |

| T11 | Resolve照合 | 同一ノード位置のOFXとcubeをfloat画像へレンダーし比較 | T10内。負/1超出力の保持も確認。格子点だけでは合格にしない |

| T15 | ホスト操作 | 候補/レシピのUndo/Redo、保存とDRP再読込、診断ON | グループ操作単位で復元。診断警告を保持。診断ON時LUT不可 |

ランダム点は一様DWG/DI点に加え、低クロマ、肌色域、黒付近、ゲート境界を重点抽出する。レシピごとのLUT検証セットは固定seedとし、開発時の最適化セットとは別にする。全12均等混合など初版に存在しない機能の試験は要求しない。

### 12.2 視覚試験

許諾済み人物、複数の肌色と照明、白い衣装、草木、商品色、夕景、低照度、ネオン、強いハイライトを含む最低30クリップの静止代表フレームと、動きのある最低10クリップを用意する。§8の全配合に加え、保護ON/OFF、Color/Toneの端点と中間値を評価する。

色の専門家2名以上が、事前承認したターゲットと照合する。重大な肌の緑化、白の蛍光化、黒の反転、境界の段差が1件でも再現すれば未合格。創作意図による色付けと不具合はターゲットで区別する。基底の好みは数値色差だけで判定しない。

### 12.3 性能目標

G0で実機を確保する。初期参照候補はMacBook Pro M2 Pro/32 GB、およびWindows 11・RTX 3060 12 GB・RAM 32 GB。別機種へ変更する場合は同等性を記録し、測定の前に固定する。OS・Resolveパッチ版・ドライバ・電源モードを報告する。

| 指標 | 受入目標 | 条件 |
| --- | --- | --- |
| 定常GPU色処理 | UHD 3840×2160、p95≤20 ms/frame | yorozu-fx 1ノード、診断OFF、ウォームアップ後1000フレーム。コーデック/I/Oは別計測 |
| ホスト再生 | UHD 24 fps、60秒間yorozu-fx起因のドロップなし | 事前キャッシュ済み素材、他の重いFXなし。無適用基準と比較 |
| パラメータ応答 | 最終入力から表示までp95≤100 ms | 合成LUT更新を含む。ホスト更新頻度も記録 |
| プラグイン追加メモリ | 共有パック＋有効1インスタンスで256 MiB以下 | Resolve全体のメモリとは区別。複数ノードのキャッシュ上限も測定 |
| LUT出力・検証 | 33は10秒以内、65は30秒以内 | 10万点、両補間、ファイル保存を含む |
| 長時間安定性 | 1時間再生・スクラブ・設定変更 | ウォームアップ後の継続的なメモリ増加なし、クラッシュなし |

8K、複数GPU、他の重いFX併用の実時間処理は初版の性能保証に含めない。CPU参照が速いことや単体kernelの速度だけでホスト性能合格としない。

## 13. 商品価値の検証と販売仮説

### 13.1 比較操作試験

対象ユーザー8名以上に、許諾済みの同じ素材で「2ルックを混ぜ、肌と商品色を残し、6ショットへ展開し、再利用可能な設定を保存する」課題を実施する。Resolve標準ノード構成を全員の比較対象とし、既存購入者にはMonet等の普段の手段でも実施してもらう。順序は交互に入れ替え、事前習熟時間を揃える。

3. [Blackmagic: Resolve Color](https://www.blackmagicdesign.com/products/davinciresolve/color)／[What's New](https://www.blackmagicdesign.com/products/davinciresolve/whatsnew) — ホストの色調整とPhotoページの公開説明。
4. [Dehancer: Resolve製品一覧](https://www.dehancer.com/shop/video/davinci_resolve) — フィルム、空間効果、色パイプライン。
5. [FilmConvert](https://www.filmconvert.com/)／[CineMatch Tutorials](https://www.filmconvert.com/tutorials?Product=cinematch) — フィルム処理とカメラ合わせの役割。
6. [MONONODES Color Shift](https://mononodes.com/color-shift-dctl/)／[Look Lab Print](https://mononodes.com/looklabprint/) — 色域別Density、色と輝度の操作。
7. [Colourlab Ai 4マニュアル](https://docs.colourlab.ai/user-guide/left-panel) — 参照画像、ルール、スタイルによる作業。
8. [Blackmagic: DWG/DI仕様](https://documents.blackmagicdesign.com/InformationNotes/DaVinci_Resolve_17_Wide_Gamut_Intermediate.pdf) — 公式原色、行列、伝達関数。使用定数は配布物で版固定する。
9. [Björn Ottosson: OKLab](https://bottosson.github.io/posts/oklab/) — 知覚操作用座標の定義。yorozu-fxのマスク品質を保証するものではない。
10. [OpenFX: Parameters](https://openfx.readthedocs.io/en/main/Reference/ofxParameter.html)、[Rendering](https://openfx.readthedocs.io/en/latest/Reference/ofxRendering.html)、[Interacts](https://openfx.readthedocs.io/en/main/Reference/ofxInteracts.html) — ホスト管理の状態とGPU/独自UIのAPI契約。Resolve実装での利用可否はG0で確認する。
